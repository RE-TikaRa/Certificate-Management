# 优化建议与路线图（详细版）

版本: v1.4.0
日期: 2026-01-23

## 目标与范围
- 目标: 提升性能、稳定性与可维护性，降低 UI 卡顿与维护成本，并增强数据一致性。
- 范围: UI/服务层/数据层/导入导出/附件/AI/MCP/日志诊断。
- 不在范围: 大规模功能重构、UI 视觉重做、数据库更换。

## 方法与前置检查
- 先建立“基线数据”：启动时间、总览页检索延迟、导入/导出耗时、附件导入耗时、内存峰值、重建索引耗时。
- 每个优化点都要有“可验证指标 + 回归检查项”，避免只改代码不改体验。
- 代码改动保持最小化，删除旧逻辑避免“兼容性堆积”。

## 项目结构要点（与优化强关联）
- UI: `src/ui/...` (PySide6 + QFluentWidgets)。
- 服务层: `src/services/...`。
- 数据层: `src/data/...` (SQLite + SQLAlchemy + FTS5)。
- MCP: `src/mcp/...` (stdio/SSE/Web)。
- 资源: `src/resources/...`，数据样例 `docs/...`。

## 优先级评估维度
- 体验影响: 是否引发 UI 卡顿/用户可感知慢。
- 风险级别: 数据一致性与可恢复性。
- 成本: 改动范围、回归风险、测试复杂度。
- 收益: 见效速度与可量化程度。

## 详细优化建议（超级细节）

### 1) FTS 一致性与全文索引维护
- 现状: FTS 依赖手动 upsert/delete（`src/data/database.py` + 服务层）。
- 风险:
  - 任何新增入口如果漏写 FTS 更新，搜索结果会与数据不一致。
  - “重建索引”成本高，且可能中断用户操作。
- 优化方向:
  1) 将 FTS 维护集中到统一入口，避免分散在多个 service。
  2) 设计可重放的“增量索引更新”机制。
- 具体措施:
  - 在 `Database` 层提供 `update_award_fts(award_id)` / `delete_award_fts(award_id)` 等统一方法。
  - 在 `AwardService` 中调用统一入口，服务层禁止直接操作 FTS 表。
  - 对导入/批量写入提供批处理更新接口（例如 `bulk_update_fts(ids)`）。
  - 预留一个“重建索引”的后台任务，支持进度与取消。
- 风险与验证:
  - 风险: 统一入口误用导致索引缺失。
  - 验证: 批量创建/删除荣誉后，FTS 搜索与列表数量一致；索引重建前后结果一致。
- 相关位置:
  - `src/data/database.py`
  - `src/services/award_service.py`
  - `src/ui/pages/overview_page.py`（触发重建）

### 2) 总览页检索/筛选/排序迁移到服务层 + 异步
- 现状: 过滤/排序/分页逻辑运行在 UI 线程（`src/ui/pages/overview_page.py`）。
- 风险: 大数据时 UI 卡顿，查询上限固定导致体验不稳定。
- 优化方向:
  - 过滤、排序、分页在服务层完成，并通过异步/后台线程回填 UI。
- 具体措施:
  - 新增 `AwardsQueryParams`（过滤条件、排序、分页）数据结构。
  - `AwardService.list_awards(params)` 内部完成排序、过滤、分页。
  - UI 侧只负责发起查询、展示加载状态、接收结果。
  - 提供“查询取消”能力（UI 切换条件时取消上一请求）。
- 细节建议:
  - 统一排序枚举，避免 UI/服务层各自维护逻辑。
  - 分页参数在服务层校验（page_size、page_index）。
  - 当查询无结果时仍返回“总数=0”，避免 UI 误判状态。
- 风险与验证:
  - 风险: UI 与服务层参数不一致导致结果错乱。
  - 验证: 组合筛选/排序与 UI 结果一致，分页准确，切换条件不阻塞 UI。
- 相关位置:
  - `src/ui/pages/overview_page.py`
  - `src/services/award_service.py`
  - `src/services/statistics_service.py`（有相似模式可复用）

### 3) 录入页与详情编辑页重复逻辑收敛
- 现状: 录入页与编辑页字段收集/校验/保存逻辑重复。
- 风险: 行为漂移、修一次 bug 要改多处。
- 优化方向:
  - 抽出“统一表单组件 + 统一字段映射”。
- 具体措施:
  - 建立 `AwardFormWidget`（含字段、校验、读取/写入 API）。
  - 将 `EntryPage` 与编辑对话框复用同一表单组件。
  - 将“成员字段 10 项规则”抽成常量，避免多处硬编码。
- 风险与验证:
  - 风险: 迁移过程中字段缺失或映射错误。
  - 验证: 新建/编辑对同一奖项得到一致结果；成员字段完整且排序正确。
- 相关位置:
  - `src/ui/pages/entry_page.py`
  - `src/ui/pages/overview_page.py`（编辑对话框）
  - `src/ui/widgets/...`（新增表单）

### 4) 附件 MD5 计算去重与缓存
- 现状: UI 阶段与保存阶段重复计算 MD5，且同一文件可能多次计算。
- 风险: 大文件慢、UI 卡顿、重复 I/O。
- 优化方向:
  - 将 MD5 计算集中到 `AttachmentManager` 并缓存结果。
- 具体措施:
  - 新增“文件指纹缓存”：key 使用 `absolute_path + mtime + size`。
  - UI 只请求 `AttachmentManager`，禁止直接计算 MD5。
  - 保存时若缓存存在直接复用，避免重复读取文件。
- 风险与验证:
  - 风险: 修改文件但 mtime 未更新导致指纹错误（极少）。
  - 验证: 重复导入同一附件不重复计算，变更文件后指纹更新。
- 相关位置:
  - `src/services/attachment_manager.py`
  - `src/ui/pages/entry_page.py`
  - `src/ui/pages/overview_page.py`

### 5) 导入/导出内存与性能优化
- 现状: `pandas` 全量读入，数据量大时占用高。
- 风险: 内存峰值不可控，导入长时间无反馈。
- 优化方向:
  - 分批读取、分批写入、流式处理。
- 具体措施:
  - CSV 使用 `chunksize`，逐块校验 + 写入。
  - XLSX 使用分片读取（如 `openpyxl`/`pyxlsb` 方式，视依赖情况）。
  - 导入过程提供 ETA/进度并允许取消。
  - 预检（dry-run）与正式导入共享同一解析逻辑，只在写库时分流。
- 风险与验证:
  - 风险: chunk 之间状态不一致（比如重复项判断）。
  - 验证: 预检与正式导入结果一致；大文件导入内存稳定。
- 相关位置:
  - `src/services/import_export.py`
  - `src/ui/pages/settings_page.py`（导入/导出界面）

### 6) 成员快照语义清晰化
- 现状: 更新成员时同步修改历史“快照”姓名。
- 风险: 破坏“历史时点一致性”与审计语义。
- 优化方向:
  - 明确 `AwardMember` 是快照还是引用。
- 具体措施:
  - 如果定位为快照：不再更新历史记录，仅新荣誉写入最新信息。
  - 如果定位为引用：在界面上明确标注“历史记录会随成员更新”。
  - 提供一次性“批量同步历史记录”的手动操作按钮，避免自动修改。
- 风险与验证:
  - 风险: 用户期望与实际行为不一致。
  - 验证: 修改成员后旧荣誉显示逻辑符合预期设定。
- 相关位置:
  - `src/data/models.py`（AwardMember）
  - `src/services/member_service.py`
  - `src/ui/pages/management_page.py`

### 7) 后台任务统一调度与取消机制
- 现状: 统计刷新/异步任务缺乏统一取消与节流控制。
- 风险: 多个任务叠加造成 UI 卡顿或线程堆积。
- 优化方向:
  - 统一一个“后台任务调度器”，提供取消、去重和节流。
- 具体措施:
  - 在 `async_utils.py` 中引入任务 key，后发任务自动取消前一个同 key 的任务。
  - 增加统一的“任务队列 + 最大并发数”控制。
  - UI 触发时先取消旧任务再启动新任务。
- 风险与验证:
  - 风险: 任务取消后 UI 状态未更新。
  - 验证: 快速切换筛选条件不会堆积任务；CPU 占用稳定。
- 相关位置:
  - `src/ui/utils/async_utils.py`
  - `src/ui/pages/dashboard_page.py`

### 8) 统一配置读取与缓存策略
- 现状: settings 查询散落在多处 service 与 UI 中。
- 风险: 多处读写导致逻辑分散、状态不一致。
- 优化方向:
  - settings 只通过 `SettingsService` 访问，并具备缓存和失效策略。
- 具体措施:
  - 在 `SettingsService` 中引入“短期缓存 + 手动失效”。
  - UI 页面初始化时一次性读取必要配置。
  - 设置变更后主动广播刷新（已存在主题变更机制可借鉴）。
- 风险与验证:
  - 风险: 缓存失效导致读取旧值。
  - 验证: 改设置后 UI 立刻生效，不依赖重启。
- 相关位置:
  - `src/services/settings_service.py`
  - `src/ui/pages/settings_page.py`

### 9) AI 证书识别稳定性与可观测性
- 现状: 多 Provider / Key 轮换，但失败时不自动重试下一个 Key。
- 风险: 单 Key 异常导致识别失败，用户无清晰错误原因。
- 优化方向:
  - 对“临时失败”进行有限重试，并可观测。
- 具体措施:
  - 为识别任务增加“最多 1 次备用 Key 重试”的策略（可配置）。
  - 失败记录写入日志或 UI 详情，方便用户定位。
  - 对 PDF 转图片页数限制给出明确提示。
- 风险与验证:
  - 风险: 重试导致成本增加。
  - 验证: 失败率下降且可追踪错误原因。
- 相关位置:
  - `src/services/ai_certificate_service.py`
  - `src/services/ai_provider_service.py`
  - `src/ui/pages/settings_page.py`

### 10) MCP 安全与资源占用控制
- 现状: 支持 stdio/SSE/Web，SSE/Web 可能常驻。
- 风险: 非预期端口占用、日志膨胀、潜在暴露风险。
- 优化方向:
  - 更明确的资源限制与日志轮转策略。
- 具体措施:
  - 增加 MCP Web/SSE 进程的“空闲自动关闭”选项。
  - 日志文件上限与轮转（按大小/天数）。
  - 启动失败给出详细提示（端口占用、权限等）。
- 风险与验证:
  - 风险: 自动关闭误伤实际使用。
  - 验证: 常驻场景不影响使用；闲置时自动释放端口。
- 相关位置:
  - `src/mcp/runtime.py`
  - `src/mcp/web.py`
  - `src/mcp/server.py`

### 11) 日志体系与诊断工具
- 现状: 使用 loguru，但错误场景反馈有限。
- 风险: 线上问题难定位。
- 优化方向:
  - 关键路径记录“可定位”日志。
- 具体措施:
  - 为导入/导出、AI 识别、备份/恢复、MCP 启停添加结构化日志字段。
  - 日志中记录请求耗时与关键参数（脱敏）。
  - 设置页提供“一键导出日志”入口（可选）。
- 风险与验证:
  - 风险: 日志过多影响性能。
  - 验证: 日志量可控，关键异常可快速定位。
- 相关位置:
  - `src/logger.py`
  - `src/services/*`
  - `src/ui/pages/settings_page.py`

### 12) 备份/恢复与数据安全
- 现状: SQLite 备份 + zip，恢复会覆盖数据库。
- 风险: 操作失误导致数据覆盖。
- 优化方向:
  - 引入“恢复前自动备份”策略强化。
- 具体措施:
  - 恢复前固定做一次临时备份，并标记时间戳。
  - 恢复完成后对关键表做数量一致性检查。
  - 如恢复失败自动回滚至临时备份。
- 风险与验证:
  - 风险: 额外备份耗时。
  - 验证: 失败恢复后仍可回到原状态。
- 相关位置:
  - `src/services/backup_manager.py`
  - `src/ui/pages/settings_page.py`

### 13) 类型检查与质量闸门
- 现状: ruff/pyright 已配置，但流程不一定固定执行。
- 风险: 规模增长后缺陷引入率升高。
- 优化方向:
  - 将 lint/format/typecheck 作为固定流程。
- 具体措施:
  - 增加本地脚本 `scripts/check.ps1`（可选），统一执行。
  - 在 README/AGENTS 强调“提交前需跑检查”。
- 风险与验证:
  - 风险: 开发流程变慢。
  - 验证: 运行耗时可接受，新增 bug 降低。
- 相关位置:
  - `docs/AGENTS.md` / `README.md`（如存在）

### 14) UI 体验细节（不改视觉风格）
- 现状: 异步任务多，用户不一定知道正在处理。
- 风险: 用户误判“卡死”。
- 优化方向:
  - 增加明确的加载状态与取消入口。
- 具体措施:
  - 总览页查询添加“加载中”状态与取消按钮。
  - 导入/导出过程中显示 ETA 与可取消。
  - AI 识别时显示当前 provider 与重试状态。
- 风险与验证:
  - 风险: UI 复杂度上升。
  - 验证: 用户操作更可预期，误操作减少。

## 路线图（建议实施顺序）
1) P0: 总览页检索异步化 + FTS 维护统一（高收益/高体验）
2) P1: 导入/导出分批 + 附件指纹缓存（性能与稳定性）
3) P1: 表单复用与成员快照语义明确（维护性）
4) P2: MCP 资源控制 + 日志增强 + 任务调度器（稳定性）
5) P3: UI 体验小优化（可选）

## 验证清单（每次改动必过）
- 搜索结果与数据一致性（FTS vs 列表）。
- 大数据量下查询不卡 UI（快速切换筛选条件）。
- 导入/导出正确性（预检与正式一致）。
- 附件导入不重复计算指纹。
- 成员更新不会意外修改历史记录（或行为符合设定）。
- 备份恢复可回滚。
